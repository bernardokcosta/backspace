# Spec: 25-language Backspace and Juno localization

## Status and objective

The user approved the practical international-app language list below, including
the five existing languages without duplication. They also explicitly require
an audit of all existing UI text and translations, native-sounding terminology,
consistent language names, and an Automatic system-language preference.

This is the written specification for approval before implementation. This phase
changes documentation only. Earlier Juno/settings/music work stays untouched;
there is no authorization for commit, version bump, push, release or deployment.

Two different acceptance rules must not be confused:

1. **This delivery:** every current app-owned user-visible text is localizable
   and the complete current feature set is translated into all 25 languages,
   including a contextual audit of the existing five. English fallback does not
   count as a completed translation.
2. **Future features:** English source copy is mandatory; translations into the
   other languages may follow later. A missing translation renders the English
   value, never a raw key, blank label or fake copied-English translation.
   Existing users keep their selected language. Proper plural families and
   placeholders remain mandatory wherever a translation is actually supplied.

this document. Work may be batched by surface/language, but partial batches are
not represented as a finished 25-language delivery.

## Product scope and exclusions

- Audit app-owned visible text in login/register/invites, chat/DM, spaces/social,
  voice/video/screen sharing/soundboard, Juno and its complete guide/settings,
  appearance/account/privacy/accessibility settings, admin/federation/search,
  uploads, errors/notices/tooltips/accessibility labels, notifications, mobile
  navigation, desktop tray/menu/update/recovery/instance-picker surfaces.
- Preserve English as the bundled, always-available fallback. Do not replace
  missing keys with literal English scattered through components.
- Juno Automatic continues following Backspace. Explicit Juno language stays
  independent of the app; it must not change document language or native menus.
- Preserve existing device-local Juno preferences, independent volume controls,
  approved music gain and foreground-only pause/resume behavior. Preserve the
  complete illustrated guide, original card examples, scroll-aware contents,
  action-card/special-card categories and current game/capability-aware rules.
  Localization is not authorization to simplify or remove these features.
- Dubbing, spoken clips and artwork/card-printed text are **not** translated or
  regenerated. Only supplied pt-BR media remains available, with consistent
  language labeling. Translating its selector labels does not create new media.
- User-authored messages/names/descriptions, externally supplied content, device
  names, protocol identifiers and OS-owned permission prompts are not silently
  machine-translated. App-owned text around them is in scope. Product/protocol
  names may intentionally remain invariant with a documented rationale.
- No runtime translation service, new framework, paid service, credentials,
  database/schema or federation/wire change. Ask before any such expansion.

## Quality, completeness and honest claims

Natural language quality is a separate gate from key coverage. Require contextual
review, terminology/style consistency, plural/grammar checks and rendered UI
inspection, including the existing English source and four translations. In
Brazilian Portuguese, use the community term **bot**, not a blanket mechanical
translation to “robô”; an actual robot/robot emoji is still a robot. Do not use
global replacements that erase meaningful distinctions.

The completion report records the English baseline/key-family inventory, locale
coverage, reviewed surfaces, checks/captures and remaining limitations. Do not
claim native-speaker/professional human review unless it actually occurred, or
promise absolute linguistic perfection merely because tests passed. No locale
is marked complete using English fallback, empty values or copied source prose.

## Current project facts and architectural note

- Existing web i18n already has a canonical registry, English bundled resources,
  lazy target catalogs, scoped Juno instances, typed keys and formatters. Reuse
  these seams; do not introduce a parallel localization framework.
- Current English inventory: 15 namespaces, 2,811 string leaves, approximately
  14,491 source words. Counts will change during extraction/new Automatic copy;
  measure the final baseline rather than hardcoding these counts as acceptance.
- `scripts/i18n-pending.txt` currently contains comments only. That is useful
  evidence, not proof of complete extraction: review literal allowances, dynamic
  labels/errors and desktop HTML/native text too.
- Current `checkParity` blocks missing target keys/namespaces. This conflicts
  with the user's **future English-only requirement**, so split mandatory
  validity/source checks from strict completeness reporting, rather than
  disabling localization checks wholesale.
- Desktop has lightweight native catalogs and inline recovery/picker text, not
  a renderer dependency on i18next. Its package has no shared workspace runtime
  dependency and compiles CommonJS with rootDir `src`. Preserve that packaging
  boundary; enforce registry/native coverage consistency through existing-style
  checks rather than importing uncompiled web/shared TypeScript into Electron.
- Automatic needs preference mode separate from resolved language. Native UI
  must not persist an Automatic choice as a frozen resolved explicit language.
  The narrow OS-language bridge extension and its security/compatibility tests
  are specified in the runtime module before any preload/IPC modification.

## Common commands and delivery gate

```sh
pnpm build
pnpm typecheck
pnpm check:i18n
pnpm lint
pnpm --filter @backspace/desktop build:ts
pnpm --filter @backspace/server typecheck:e2e
pnpm --filter @backspace/web test -- src/i18n
pnpm --filter @backspace/desktop test -- src/l10n.test.ts
```

Use established Windows wrappers and isolated test profiles/storage where
needed. Exact new test/strict-completeness command paths belong in the plan.
The web i18n suite includes the existing checker tests at
`packages/web/src/i18n/check.test.ts`.
Build shared → server → web sequentially. Update affected localization/design/
desktop/security subsystem docs with the implementation, and Docker COPY paths
if a build-time check reads a new file not included by the current image.

No locale is advertised as completed before all three modules meet their gates.
Final review must cover the entire source/catalog/config/native/docs/helper
delta, not merely the last language added. Local preview/testing is authorized
after spec approval; publication/deployment is not.
