# Desktop 1.15.1: SDR capture and required updates

**Date:** 2026-10-24
**Status:** Specification and plans approved by the user; inline implementation in progress
**Target release:** Backspace Fork 1.15.1

## Objective and confirmed decisions

An HDR monitor currently produces an overexposed screen share. Add a real
**Force SDR** capture option without turning off the monitor's HDR setting.
Also require desktop **1.15.1 or newer** on the operator's instance, while
leaving browser access available. Correct the release process before enforcing
that requirement so nobody is blocked without an available installer.

The user approved these decisions in conversation:

- Block the entire outdated desktop experience, not just screen sharing.
- Keep access through an ordinary browser available.
- Publish and verify installers before enabling the minimum-version policy.
- Add a native Windows capture implementation; retain existing capture on
  other platforms.

Assumptions made by the implementer, not additional user requirements:

- Force SDR is initially opt-in and saved on the device; absent settings mean
  off, preserving existing captures.
- Changing Force SDR requires a new screen-share capture, not an application
  restart. A live share's control explains this rather than silently changing
  only its saved preference or unexpectedly interrupting viewers.
- The minimum version is an instance operator setting, initially disabled in
  source defaults. Deployment explicitly enables `1.15.1` after release checks.
- No purchasing certificates, new operating-system platforms, database
  migration, or monitor/Windows HDR configuration changes are included.

Build order: prove native capture feasibility → implement and validate SDR
capture → implement and validate minimum-version enforcement → consolidate
and verify the 1.15.1 release → deploy → enable the minimum version.

The rollout ordering is an operational prerequisite, not a circular code
dependency: minimum-version code does not call release automation.

## Existing architecture and seams

- `packages/desktop/src/main.ts` owns Electron's display-media permission
  handler and updater. `preload.ts` exposes a restricted bridge to a sandboxed,
  context-isolated renderer loading the instance's web client.
- `packages/web/src/utils/screenShare.ts` stages a capture before publication.
  Setup preview and the published share must use the same corrected video.
- `StreamQualityControls.tsx` is shared by setup and live-share settings;
  `voiceStore.screenShareConfig` owns saved capture preferences.
- `updateStore.ts` already reads the installed desktop version through
  `getVersion()` and supports older bridges. It mirrors the actual updater's
  `auto`, `manual` and `external` capabilities rather than assuming that every
  platform can install an update.
- `GET /api/instance/info` provides public instance policy. Its optional new
  field must remain compatible with older instances and clients.
- The current release matrix publishes independently through electron-builder.
  The 1.15.0 operation observed assets split between release ids `422966942`
  and `422967962`. The first was later observed as an untagged draft. This is
  evidence of the failure, not a confirmed explanation of its cause.

## Tech stack and project structure

Keep TypeScript strict, React 19, Zustand 5, Fastify 5, Electron 45 and the
existing LiveKit integration. Build tooling uses Node 24 and pnpm 10.34.3.
The native Windows module uses the Windows SDK and the existing Windows build
toolchain; any added dependency needs a stated purpose and compatible license.

Expected ownership, not an instruction to refactor unrelated files:

- `packages/desktop/native/`: native Windows capture and conversion code/tests.
- `packages/desktop/src/`: narrow capture adapter, IPC policy, updater integration.
- `packages/desktop/scripts/`: native build and packaged-module verification.
- `packages/web/src/utils/`: capture integration and version-policy helpers.
- `packages/web/src/components/`: existing stream controls and required-update UI.
- `packages/shared/src/`: shared version comparison and wire types if required.
- `packages/server/src/`: validated operator setting and desktop policy checks.
- `.github/workflows/` and `scripts/`: single-writer publication and artifact checks.
- `docs/systems/`: update affected desktop, security, voice, API, WebSocket,
  deployment and localization contracts in the implementation changes.

## Code style and localization

Use small, explicit discriminated results at privileged seams, matching the
existing capability-driven audio and updater code. For example, a capability
answer has a supported/unsupported result with a finite reason, not `any`, a
silent fallback, or a platform guessed by the renderer.

```ts
type SdrCaptureCapability =
  | { supported: true }
  | { supported: false; reason: 'platform' | 'system' | 'module' | 'transport' };
```

This describes the required interface shape, not implemented exports. Exact
function names belong in the implementation plan. Every visible string uses
the existing catalogs, including Brazilian Portuguese, with consistent keys
for all shipped languages. Follow Aether Drift rather than adding a new theme.

## Testing strategy and acceptance gates

- Unit tests for version ordering, policy decisions, updater state transitions,
  persisted-setting migration, capture consent and cleanup.
- Native tests with known HDR/scRGB inputs and SDR reference outputs, plus
  actual Windows capture/load tests. Mock tests do not prove HDR correctness.
- Component tests for browser bypass, outdated/unknown versions, failure/retry,
  download progress, manual/external updates and restart availability.
- Server tests for REST/WebSocket policy behavior without affecting browser,
  bot or server-to-server federation traffic.
- Release-fixture tests for missing files, duplicate names, incorrect versions,
  hash mismatches, partial builds and reruns.
- Real packaged Windows tests on x64 and arm64, with recorded distinction
  between compile-only, load-only and hardware capture validation.
- A real HDR display comparison must show corrected preview and received SDR
  video with HDR still enabled, plus an SDR-monitor regression check.
- Capture feasibility, safe frame transport, correct native packaging and
  real HDR validation are release gates. Report an unavailable hardware check
  as pending; do not label the feature verified or activate the version block.
- Mandatory external final review covers all implementation, workflow,
  configuration and deployment changes before final delivery.

## Boundaries

**Always:** preserve source consent and Electron isolation; bound native/GPU
resources; validate cross-process data; preserve fork identity and source
offer; retain safe updater recovery; snapshot production before changes.

**Ask first:** introduce a different platform/runtime or a new dependency with
material licensing/operational impact; weaken any security posture; change
the agreed minimum version or expand enforcement beyond desktop users.

**Never:** replace tone mapping with a cosmetic gamma/brightness checkbox;
disable Windows HDR; expose raw native handles to the remote page; disable
the sandbox; commit runtime data/secrets; overwrite existing release artifacts
silently; enforce a version whose installers have not passed release gates.

## Approval and open items

No additional product choice is requested. Technical items to resolve and
record before implementation is considered complete:

1. Supported sandbox-preserving frame transport in the pinned Electron build.
2. Native Windows capture/tonemapping behavior and packaged x64/arm64 loading.
3. Actual identification of previously shipped desktop clients and convergence
   of already-open sessions onto the blocking update screen.
4. A real HDR-monitor validation session; absence of hardware is a blocker to
   claiming the color issue fixed, not permission to skip the check.

This specification is a design artifact only. It does not publish 1.15.1,
change production, or activate any minimum-version policy.
