### Actual baseline cookie mode / explicit maintainer decision

Candidate run `42553666839` again passed all build/16-asset gates; its six
installed jobs stopped at the unconditional baseline encryption assertion.
PR CI `42553666887` was fully green, including both native Windows architectures.
No tag, merge, public release or production deployment occurred.

Read-only extraction of the SHA-256-verified 1.16.8 Linux `.deb` and the actual
candidate `.deb` measured **cookie encryption Disabled in both**. RunAsNode and
Node inspector stayed Disabled, OnlyLoadAppFromAsar Enabled. No executable was
run or fuse changed locally. [Electron documents cookie encryption as opt-in](https://www.electronjs.org/docs/latest/tutorial/fuses),
and warns that enabling it is a one-way transition. The fixture had assumed a
protection the baseline did not provide.

The maintainer explicitly chose **“Preservar modo (Recomendado)”**: retain the
existing protection and compare actual mode/data rather than add encryption.
The spec/plan now record that clarification. The gate reuses the pinned fuse
reader (existing dependencies installed with lifecycle scripts disabled), rejects
all baseline/candidate mode changes/unknown values, and checks persisted cookies
according to the measured mode. Encrypted baselines still require encrypted
storage, working recovery and Linux keyring—not the basic fallback. Plaintext
baselines require the exact persisted marker and are reported plaintext, with
`encryptedCookie:false`; no encrypted-profile PASS is invented. AppImage binaries
are read after extraction on the guarded runner without modifying them. Every
other preservation, identity, native, security and publication gate remains.

The mode-aware validation correction passes all 121 Node/Flatpak tests and lint;
diff checks pass. Dependency versions/lockfile and the production fuse-flipping
hook are unchanged. The explicit maintainer decision and read-only library API
were checked by the implementer; no third external review was invoked beyond the
two-call limit. Real installed results for this corrected predicate remain pending.
