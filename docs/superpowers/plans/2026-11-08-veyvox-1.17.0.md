# Veyvox 1.17.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship Veyvox 1.17.0 as a compatible replacement for this fork, with new artwork, bilingual documentation and a verified public release.

**Architecture:** Keep existing product, persistence and release owners. Separate visible branding from installed/cryptographic identities, and prove preservation before renaming consumers. Four subplans converge on one validated release commit; no production deployment is included.

**Tech Stack:** TypeScript strict, pnpm 10.34.3, Node >=22.12.0 (local/Docker Node 24; CI 22/24), React 19, Fastify 5, Electron ^45.2.1, electron-builder ^26.18.0, existing Sharp/ICO/ICNS encoders, GitHub CLI/Actions.

**Spec:** [approved parent](../specs/2026-11-08-veyvox-1.17.0.md) and its four linked module specs.

## Global Constraints

- Public product name: `Veyvox`; canonical project/package slug: `veyvox`.
- Target repository: `bernardokcosta/veyvox`, same owner, visibility and history.
- Version **1.17.0**; only new immutable tag **v1.17.0**; preserve all prior tags/releases.
- No new dependencies; no database schema, credential, federation identity or permission change.
- Keep all 25 languages, Aether Drift primary `#7c6cf6`, and Juno artwork/rules/music/dubbing unchanged.
- Preserve supplied masters; derive cleanup/framing reproducibly. Move only the two authorized PNGs.
- Never read checkout `.env` or real runtime `data/` in tests; use temporary profiles/storage and loopback.
- Build order remains shared → server → web. Do not parallelize those builds.
- Do not deploy, force-push, weaken security/release gates, recreate the old repository slug, or claim unexecuted acceptance.
- Module commit checkpoints are **queued**, not executed immediately: the approved spec requires full-scope external Sol review before any implementation commit. Stage only explicit intended paths afterward.

## Review Focus

- Renamed package metadata silently changes an encrypted profile/install identity: C1/C5 compare baseline and candidate, not just source strings.
- Interrupted/cross-device migration leaves a nonempty partial profile: C1 tests failed copy/promotion and repeated startup.
- Mixed old/new shells and hosted clients lose native operations: C2/C3 exercise both bridges and both link schemes.
- Self-hoster updates pull another image or start a second stack: C4/R2 retain registry/service/project/data identities.
- A green candidate is mistaken for a published, usable release: R4 verifies anonymous feeds/assets and the exact final SHA.
